# Feature: Seat booking

**Branch:** `feature/booking`
**Depends on:** `plans/tours.md` (Tour entity with denormalized `bookedCount`, ToursService/controllers, tours store, ToursView/TourDetailView, `tour-time.ts`), `plans/auth-and-roles.md` (JwtAuthGuard, RolesGuard, `@Roles`, `@CurrentUser`, AuthUser, auth store), `plans/foundation-ui-kit.md` (`AppDialog`, `DataTable`, `EmptyState`, `Tag`, `AppButton`, `seatTagState`)

## Goal

A hiker opens a tour, clicks a now-live "Book a seat", confirms the "Book one seat?" dialog, and holds a seat — the tour flips to "✓ Seat booked" / "You are in", and the booking appears in the My bookings table at `/my`. Booking is capacity-safe under concurrency: two hikers racing for the last seat can never both win. A hiker can cancel via the API up to 24 h before the start; the owning guide sees a real Roster on the tour detail page.

## Decisions (binding for this slice)

1. **`bookedCount` stays the denormalized counter on `Tour`** (per `plans/tours.md` Decisions #2). Booking increments it and cancelling decrements it inside the capacity-guarded transaction; it is **never** replaced by a `COUNT(*)` over bookings. `Booking` rows are additive — they drive the roster and `isBookedByMe` only. Consequence for seeds: seed tour 1 shows "9 / 12 booked" while its roster lists 4 seeded participants — that mismatch is accepted and deliberate (the design's counts exceed its 8 hiker users). Real bookings move both the counter and the rows together.
2. **Concurrency strategy: conditional `UPDATE … WHERE bookedCount < capacity` checking affected rows**, inside a `dataSource.transaction`. Chosen over `SELECT … FOR UPDATE` because the `UPDATE` itself takes the row lock: a second racer blocks on the tour row, re-evaluates the predicate after the first commit, affects 0 rows, and its whole transaction (booking insert included) rolls back — same serialization, less code, no explicit lock mode, no deadlock window against the cancel path. The unique index on `(tourId, hikerId)` is the race-safe double-book check (Postgres error `23505` → 409), not a pre-`SELECT`.
3. **Status codes**: booking a full tour, booking twice, and booking a tour that has already started are all **409 Conflict** (messages: `'Tour is full'`, `'You already booked this tour'`, `'Tour has already started'`). Cancelling within 24 h of start is **409** (`'Bookings can only be cancelled up to 24 h before the tour starts'`) — a state conflict, not a permission failure. Cancelling a booking that is not yours or does not exist is **404** in both cases, so booking ids never leak. Successful cancel is **204 No Content**.
4. **Tour start instant** = server-local `new Date(\`${tour.date}T${normalizeTime(tour.startTime)}:00\`)` (reuse `normalizeTime` from `tour-time.ts`; Postgres returns `HH:MM:SS`). Book requires `start > now`; cancel requires `start - now >= 24 h`. Local time, not UTC, matching the `today()` convention in `ToursService`.
5. **Optional token awareness** via a new `OptionalAuthGuard` extending `JwtAuthGuard`: it awaits `super.canActivate()` in a try/catch and returns `true` on any failure (missing header, bad token, deleted user), leaving `request.user` unset. The tour GET endpoints stay public; when a valid token is present the service decorates per-viewer. `@CurrentUser()` already returns `request.user` as-is, so it yields `undefined` for anonymous callers — declare the param `AuthUser | undefined`.
6. **`isBookedByMe`** is computed with **one** query per decoration pass: `SELECT tourId FROM bookings WHERE hikerId = :viewer AND tourId IN (…)` over the fetched tours — never per-tour (N+1). Anonymous viewer → all `false` (today's behavior, unchanged).
7. **`roster` appears whenever the viewer is the owning guide** (`viewer.id === tour.guideId`), on any endpoint returning a single decorated tour — `GET /api/tours/:id` and the `201` from scheduling one, since the scheduling guide is by definition its owner. (An earlier draft of this decision said "only on `GET /api/tours/:id`", which contradicted T5's read-back and made the tours e2e fail; the rule is about the *viewer*, not the endpoint.) List endpoints never carry it. It is an optional field added additively to `TourDto` — every existing field and consumer is untouched. Owning guide with zero bookings gets `roster: []`; everyone else gets no `roster` key at all. Entries carry raw `bookedAt` ISO timestamps; the frontend formats "booked {n} days ago".
8. **`GET /api/bookings/mine` uses `JwtAuthGuard` only** (no role guard): it is ownership-scoped by `hikerId = caller`, so a guide simply gets `[]` — this keeps `/my` renderable for both roles without a 403. `POST /api/tours/:id/bookings` is hiker-only (`@Roles('HIKER')`), per spec §6. "Mine" returns **upcoming tours only** (`tour.date >= CURRENT_DATE`, matching the sub-copy "Seats you hold on upcoming guided tours"), ordered `tour.date ASC, tour.startTime ASC`.
9. **`POST` returns a `BookingDto`** — `{ id, status, createdAt, tour: TourDto }`, the same item shape `GET /bookings/mine` lists, with `tour` re-read after commit so it carries the incremented `bookedCount` and `isBookedByMe: true`.
10. **Seed bookings: yes** — an in-code `SEED_BOOKINGS` constant in `seed.ts` (not in `docs/seed-data.json`, which stays verbatim design data). All 8 roster-sample hikers (spec §5) get bookings across the 5 tours, with mixed `PAID`/`CONFIRMED` and staggered `createdAt` values so "booked {n} days ago" varies. Seeding bookings does **not** touch `bookedCount` (Decision #1). Because seeded bookings were never counted into the design's counters, the cancel decrement uses `GREATEST(bookedCount - 1, 0)` as a floor.
11. **No cancel UI this slice.** The design's My bookings row has exactly one action, "View tour"; no screen offers a cancel control, and the design is the source of truth for all UI. `DELETE /api/bookings/:id` is implemented and fully tested backend-side; wiring a UI for it is deferred until a design exists (flagged to the orchestrator).
12. **Guide variant of `/my`** stays minimal this slice: heading "My tours" + sub + the dashed empty state with "Browse tours" (slice 7 owns the real guide table per spec §9). Hiker variant is fully real.
13. **Empty roster copy**: the prototype never renders an empty roster; when `roster` is `[]` the view shows the H4 plus a muted 13px line "No bookings yet." instead of an empty table (flagged as a chosen invention).
14. **Book-dialog error path**: on any API error the dialog toasts the server's 409 message when there is one (e.g. "Tour is full"), otherwise "Could not book that seat", then closes, and the view refetches the tour — the seat state changed under the user, so stale form-keeping (the schedule dialog's behavior) would be wrong here.

## API contract

`RosterEntryDto` and `BookingDto` (new); `TourDto` from `plans/tours.md` is unchanged except for two additive semantics:

```json
// TourDto additions (all other fields exactly as in plans/tours.md):
{
  "isBookedByMe": true,          // real when a valid token accompanies any tour GET; false for anonymous
  "roster": [                     // ONLY on GET /api/tours/:id, ONLY for the owning guide; absent otherwise
    { "name": "Luka Horvat", "bookedAt": "2026-08-08T09:00:00.000Z", "status": "PAID" }
  ]
}
```

```json
// BookingDto
{
  "id": "uuid",
  "status": "CONFIRMED",          // "CONFIRMED" | "PAID"
  "createdAt": "2026-08-13T10:00:00.000Z",
  "tour": { /* full TourDto, isBookedByMe true, no roster */ }
}
```

- `POST /api/tours/:tourId/bookings` — **hiker-only**: `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('HIKER')`, in that order. No body. Capacity-safe transaction (Decisions #2): insert `Booking` (unique `(tourId, hikerId)`; `23505` → 409 `'You already booked this tour'`), then `UPDATE tours SET "bookedCount" = "bookedCount" + 1 WHERE id = :id AND "bookedCount" < capacity`; 0 affected rows → 409 `'Tour is full'` and full rollback. 409 `'Tour has already started'` when start ≤ now (Decisions #4). → **201** `BookingDto`; 400 non-UUID; 401 no/bad token; 403 guide token; 404 unknown tour.
- `GET /api/bookings/mine` — **authenticated** (`JwtAuthGuard` only, Decisions #8). Caller's bookings on upcoming tours, ordered `tour.date ASC, tour.startTime ASC` → **200** `BookingDto[]` (each `tour.isBookedByMe: true`, no `roster`); guide → `[]`; 401 without token.
- `DELETE /api/bookings/:id` — **authenticated**. Only the booking's own hiker: in one transaction, load booking `WHERE id = :id AND hikerId = :caller` (miss → **404**, whether unknown or someone else's), 409 when `start - now < 24 h` (Decisions #3/#4), else delete the row and `UPDATE tours SET "bookedCount" = GREATEST("bookedCount" - 1, 0)` → **204** no body; 400 non-UUID; 401 without token.
- `GET /api/tours`, `GET /api/tours/:id`, `GET /api/routes/:routeId/tours` — unchanged shape and publicness, now behind `OptionalAuthGuard`: with a valid token, `isBookedByMe` is real everywhere and `GET /api/tours/:id` adds `roster` for the owning guide (Decisions #5–#7).
